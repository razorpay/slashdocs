Operating assumptions

The review begins with the operating assumptions. Traffic is expected to arrive in two daily peaks, and the new path must tolerate one region becoming unavailable without making the authoring workflow read-only.

The proposal keeps the existing document contract: one self-contained HTML artifact, rendered inside the slashdocs sandbox, with real selectable text for review. No reviewer-specific state is baked into the document.

Request lifecycle

Each request is assigned a stable operation id before it crosses a process boundary. The id is preserved through the worker handoff and is included in every terminal response, including validation failures.

The client keeps a bounded retry budget. It retries only idempotent operations, adds jitter between attempts, and stops early when the server returns a permanent policy rejection.

Data boundaries

Document metadata and rendered assets follow separate retention paths. Metadata remains queryable for audit, while expired binary artifacts are removed by a version-aware cleanup job.

Repository credentials never enter rendered HTML. GitHub reads are brokered by the slashdocs application and return only the requested raw content to the requesting document window.

Open question Decide whether repository access failures should be cached for a short period or retried on every document refresh.
4

Readiness gates

The rollout controller evaluates service health, queue depth, and error budget consumption before it advances. A single healthy probe is not enough to move traffic.

Ownership transfers only after the readiness signal is green. Until then, the implementation team remains responsible for triage and the operations team observes without becoming the primary escalation path.

  • Baseline dashboards contain request, worker, and egress signals.
  • Runbooks identify the exact rollback and replay commands.
  • The on-call handoff includes a named incident commander.
  • Known limitations are visible in the release communication.
5

Rollout plan

Traffic moves in measured steps: internal users, one percent, ten percent, fifty percent, and finally full availability. Every step has a minimum observation period and an explicit abort threshold.

Rollback remains available for the entire observation window. The old write path is kept warm, schema changes remain backward compatible, and queued events can be replayed after a controlled downgrade.

6

Observability and diagnosis

Dashboards are organized around user-visible outcomes first. Resource saturation and dependency health remain available for diagnosis but do not replace the success-rate and latency views used for release gates.

Every alert links to a runbook and a pre-filtered diagnostic view. The alert payload includes the deployment version, cell, operation class, and the last successful rollout checkpoint.

Evidence attached The load-test trace set now covers the retry, rollback, and delayed outbox-consumer scenarios requested in the previous review.
7

Failure exercises

The team will inject dependency timeouts, stale credentials, a blocked queue consumer, and a partial regional outage. Each exercise must prove both detection and recovery rather than stopping at an alert screenshot.

The recovery drill ends only when the system has returned to steady state and the deferred work has been reconciled. A successful rollback with an unreplayed outbox is considered incomplete.

  • Dependency latency injection produces the expected timeout class.
  • Credential revocation fails closed and emits one actionable alert.
  • Consumer recovery drains backlog without breaching write latency.
  • Regional evacuation preserves operation idempotency.
8

Decision record

Reviewers should resolve or reply to every blocking thread before the decision meeting. Non-blocking follow-ups receive an owner and due date so they do not disappear when the document is versioned.

The final checkpoint records the release decision. It captures the approvers, accepted risks, rollback owner, and the exact commit deployed so the outcome can be reconstructed without relying on chat history.

Proposed decision Proceed to the internal phase after the failure exercises pass and the repository-access cache behavior is documented.
