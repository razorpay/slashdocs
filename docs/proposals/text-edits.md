# Text edits for slashdocs editors

Status: Proposed

## Summary

Let a document's owner and editors change text from the reader and publish the
changes as a new version.

Today every change is a full HTML upload. Fixing a typo means pulling the
document, editing the file, and pushing it again, or asking the agent that
wrote it. Reviewers can only point at the text with a comment.

The first release will:

- Add an **Edit** action to the selected-text toolbar for the owner and editors
  of a document, on the latest version only.
- Edit the selected text in a small editor that supports bold, italic, inline
  code, and links.
- Keep edits in the browser until the editor saves them. A refresh or a closed
  tab discards them, after the browser's unsaved-changes prompt.
- Save every edit made since the last save as one new version, through the
  existing version upload, with a change summary that lists each edit.
- Change only the edited bytes of the stored HTML. Scripts, styles, whitespace,
  and every other part of the file stay as they were.
- Need no API, schema, or permission changes.

Commenters and viewers see no change.

## Out of scope

- Suggested edits from commenters.
- Edits that span more than one block, or that add, remove, or reorder blocks.
- Editing text that a document's scripts generate at run time.
- A comparison view between versions.
- Edit commands in the CLI and MCP tools. Agents keep publishing whole
  versions.

## Experience

### Making an edit

1. The editor selects text in the latest version. The selected-text toolbar in
   the document shows **Edit** beside **Comment** and **Copy link to text**.
2. **Edit** opens an editor next to the selection. It holds the selected text
   with its formatting, buttons for bold, italic, inline code, and link, and
   **Cancel** and **Apply** (⌘↵ or Ctrl+↵).
3. **Apply** replaces the text in the rendered document at once, with a subtle
   highlight on each edited range.

When the selection starts or ends inside an element such as `<strong>` or
`<a>` that it only partly covers, the edit grows to cover the whole element,
and the editor shows the grown range. The editor never splits an element. A
selection that ends where an element's text ends, or starts where it begins,
stays inside that element.

The editor refuses a selection, with a message, when:

| Case                                                              | Message                                                                           |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| The text is not in the stored HTML, because a script generated it | This text is generated by the document and can't be edited here.                  |
| The selection spans more than one block                           | Select text within one paragraph, heading, list item, or table cell.              |
| The selection overlaps an unsaved edit                            | This text has an unsaved edit. Remove that edit from the list to change it again. |
| The viewer is on an older version                                 | Switch to the latest version to edit.                                             |

### Saving

While there are unsaved edits, the document bar shows **N unsaved edits**,
**Discard**, and **Save as version**.

- **N unsaved edits** opens a list of edits, each as old text → new text, or
  as "Formatted" and the text when only its formatting changed, with a button
  to remove it. Removing an edit reloads the document and applies the
  edits that remain.
- **Discard** removes every edit and reloads the document.
- **Save as version** asks for a change summary, prefilled with one line per
  edit, then uploads the new HTML. The reader moves to the new version. Comments
  re-anchor to it as they do for any new version.

Leaving or reloading the page with unsaved edits shows the browser's
unsaved-changes prompt.

### When someone else publishes first

The upload sends the version the edits were made on as `base_version_id`. If
another version was published since, the server answers `409
version_conflict`. The editor then offers **Re-apply edits to vN**, which
places each edit again on the newer version. An edit whose original text is no
longer there stays in the list, marked as not applied, so no edit is lost
silently.

## How an edit maps to the stored HTML

The rendered document is not the stored HTML. Documents run their own scripts,
which can add, move, or rewrite text after load. Saving the rendered DOM would
store that run-time state, so the editor never serializes the rendered
document. It edits the stored HTML instead.

1. **Load the stored HTML.** The first **Edit** fetches the latest version
   through `GET /v1/documents/{id}/versions/{version_id}/html` and keeps it for
   the session. It decodes the bytes as strict UTF-8 and keeps a byte order
   mark, so the saved file encodes the untouched text to the same bytes.
2. **Find the selection in it.** The bridge reports the selection as the same
   text-quote anchor comments use: quote, prefix, suffix, and offsets. The app
   parses the stored HTML with `DOMParser`, which runs no scripts, and resolves
   the anchor against that document with the existing anchoring code in
   `frontend/bridge/anchoring`. No match means the text is generated, and the
   edit is refused. The app resolves against the stored HTML with the unsaved
   edits applied, because the rendered document already shows them. A range
   that touches an edited range is refused as overlapping. Any other range is
   shifted back to offsets in the stored HTML by the length change of each
   edit before it.
3. **Find the byte offsets.** `DOMParser` does not report source positions, so
   the app also parses the stored HTML with
   [parse5](https://github.com/inikulin/parse5), with source locations on and
   scripting off to match `DOMParser`. Both follow the HTML parsing algorithm,
   so their text nodes line up one to one in document order. The app checks
   that the two lists match and refuses the edit if they do not. It maps
   character offsets inside a text node to source offsets with character
   references, such as `&amp;` and `&nbsp;`, taken into account.
4. **Bound the range.** Both ends of the range must have the same nearest block
   ancestor, such as a `p`, `h1`–`h6`, `li`, `td`, `th`, `dt`, `dd`,
   `blockquote`, `figcaption`, `pre`, or `div`, and the range must not hold a
   block, list, or table of its own. When an end of the range falls inside an
   inline element that the range does not fully contain, the range grows to
   include that element.
5. **Sanitize the replacement.** DOMPurify, already a frontend dependency,
   keeps only `strong`, `b`, `em`, `i`, `code`, `br`, and `a` with an `href`
   that uses `http:`, `https:`, or `mailto:`. When the original range holds
   other inline markup, such as a `span` with a class, the editor warns before
   **Apply** that the styling will be removed.
6. **Splice.** Each edit records its source start and end offsets, its
   original HTML, the anchor it came from, and its replacement. Overlapping
   edits are refused. Saving applies the edits from the end of the file to the
   start, so earlier offsets stay valid, and leaves every other byte untouched.
7. **Publish.** The new HTML goes through the existing
   `api.createVersion(docId, baseVersionId, summary, file)`. The server already
   requires the editor role and answers `409 version_conflict` when the base is
   out of date.
8. **Re-apply.** On conflict, the app fetches the newer version and repeats
   steps 2–6 for each edit, using the anchor of its original text.

## Bridge messages

The app and the bridge exchange three new messages:

| Direction    | Message                                     | Purpose                                               |
| ------------ | ------------------------------------------- | ----------------------------------------------------- |
| app → bridge | `slashdocs:edit-enabled` `{ enabled }`      | Shows or hides **Edit** in the selected-text toolbar. |
| bridge → app | `slashdocs:edit-request` `{ anchor, rect }` | Opens the editor for the selection.                   |
| app → bridge | `slashdocs:edit-preview` `{ anchor, html }` | Shows an applied edit in the rendered document.       |

**Discard** and removing an edit reload the rendered document rather than undo
previews, and **Save as version** moves the reader to the new version. The
reloaded frame receives the remaining previews in the order the edits were made.

Document scripts share an origin with the bridge, so they can forge
`edit-request`. The app takes only the anchor from the message and resolves it
against the stored HTML it fetched itself. A forged message can at most open
the editor on other text, which the editor then shows to the user. The HTML in
`edit-preview` is the sanitized replacement.

## Frontend structure

| Unit                                         | Responsibility                                                                                                 |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `src/lib/text-edits/source-map.ts`           | Parses with parse5 and `DOMParser`, pairs text nodes, and maps text offsets to source offsets.                 |
| `src/lib/text-edits/locate.ts`               | Resolves an anchor to a bounded source range and its HTML, or to `generated`, `crosses-blocks`, or `overlaps`. |
| `src/lib/text-edits/sanitize.ts`             | The DOMPurify allowlist, and detection of markup the replacement drops.                                        |
| `src/lib/text-edits/apply.ts`                | Checks overlaps, splices edits, writes summary lines, and re-applies edits to a newer version.                 |
| `src/pages/use-text-edits.ts`                | Session state: base version, stored HTML, edits, the unsaved-changes prompt, and the save and conflict flow.   |
| `src/pages/doc-text-edit-box.tsx`            | The editor next to the selection.                                                                              |
| `src/pages/doc-edits-bar.tsx`                | **N unsaved edits**, the list of edits, **Discard**, and the save dialog.                                      |
| `bridge/bridge.ts`, `bridge/edit-preview.ts` | The **Edit** action and the bridge side of the messages above.                                                 |

`doc-render-frame.tsx`, `doc-workspace.tsx`, and `doc-bar.tsx` wire these
together. The publishing model in `internal/guidelines/guidelines.go` gains a
line saying that editors can also save text edits from the UI as a new
version.

## Tests

### Unit tests

`src/lib/text-edits` tests cover:

- A typo fixed inside one text node.
- Text with character references such as `&amp;` and `&nbsp;`.
- A selection that ends inside `<strong>` grows to the whole element.
- A selection across two paragraphs is refused.
- Text added by a script is refused.
- Several edits give the same result in any order, and change no other byte.
- Overlapping edits are refused.
- The sanitizer keeps the allowed tags and drops `javascript:` links,
  attributes, and other elements.
- Re-applying edits to a changed file places the edits whose text remains and
  reports the rest.

### Component tests

The editor applies bold, italic, code, and links, and warns when the
replacement drops markup.

### Browser tests

A Playwright test in `e2e/` edits a word as the owner, saves, and checks that a
new version holds the change. A viewer sees no **Edit** action.

## Acceptance criteria

- The owner and editors can edit text on the latest version and save the edits
  as one version. Commenters and viewers cannot.
- The saved HTML differs from its base only in the edited ranges.
- Generated text, multi-block selections, and overlapping edits are refused
  with a message.
- A save against an out-of-date base offers to re-apply the edits and never
  drops an edit silently.
- `make test` and `make lint` pass.
